# JAWL · веб-консоль

Интерфейс управления фреймворком. Ядро не изменяется и не импортируется —
всё живёт в `web/` (статика) и `src/web/` (сервер), и удаляется целиком, не
задев `src/l0…l3`.

```
web/                 статика
  index.html         разметка: 5 вкладок, все контролы
  styles.css         оформление, одна таблица стилей
  console.js         поведение + слой `api` со всеми точками интеграции
src/web/             бэкенд
  server.py          aiohttp: статика + /api/config
  config_io.py       чтение/запись settings.yaml и .env
  schema.py          карта «контрол ↔ ключ конфига»
```

## Запуск

Двойной клик по `start.bat` в корне проекта — консоль поднимется и сама
откроет браузер. То же из терминала:

```bash
python -m src.web
```

Адрес по умолчанию <http://127.0.0.1:8770/>. Тесты — `tests/web/test.bat`
или `python -m pytest tests/web` из корня проекта.

### Окно консоли как индикатор

У агента нет своего окна, и без индикатора непонятно, работает он сейчас или
нет — а работающий агент тратит токены. Поэтому окно консоли само им и служит:

```
JAWL console: http://127.0.0.1:8770/
Закройте это окно или нажмите Ctrl+C — консоль остановится
вместе с агентом, если запускали его отсюда.

23:38:49  Агент запущен (PID 12316)
  • АГЕНТ РАБОТАЕТ · PID 12316 · 00:04:12 · расходует токены
```

Нижняя строка обновляется на месте раз в две секунды и красится по состоянию:
зелёным — работает, красным — остановлен, жёлтым — поднимается. Смены состояния
остаются в истории отдельными строками со временем.

Цвет включается через `ENABLE_VIRTUAL_TERMINAL_PROCESSING`: классическая консоль
Windows иначе печатает ANSI-коды как текст. Если включить не вышло или вывод
перенаправлен в файл, цвет просто не применяется — мусора на экране не будет.
Ширина строки для затирания считается по видимым символам, а не по строке с
escape-кодами, иначе хвост предыдущей строки оставался бы на экране.

**Про «Terminate batch job (Y/N)?».** Это сообщение печатает сам `cmd.exe`, когда
в пакетном файле нажали Ctrl+C. Перевести или подавить его нельзя — оно зашито
в командный процессор. Зато оно появляется уже после того, как мы завершились,
поэтому консоль поясняет его заранее: что это вопрос про `start.bat`, а не про
агента, и что агент к этому моменту уже остановлен. Пояснение печатается только
при запуске из `.bat` (проверяется по переменной `PROMPT`) — иначе вопроса не
будет и подсказка сбивала бы с толку.

**При закрытии окна агент останавливается — но только тот, которого запускала
сама консоль.** Если агент был поднят из CLI, а консоль открыли посмотреть
настройки, он продолжит работать: ронять чужой процесс она не вправе.

Флаги: `--no-browser` не открывать браузер, `--keep-agent` не останавливать
агента при выходе. Новых зависимостей нет: `aiohttp`,
`ruamel.yaml`, `pydantic` и `python-dotenv` уже в `requirements.txt`.

По умолчанию слушает только localhost. Для VPS: `--host 0.0.0.0` — тогда
автоматически генерируется токен, либо задайте свой через `--token` или
переменную `CONSOLE_TOKEN`.

`index.html` открывается и двойным кликом, но без сервера поля интегрированных
вкладок блокируются и над ними появляется предупреждение — фальшивых значений
не показывается.

## Где что искать

**Все обращения наружу собраны в одном объекте `api` в начале `console.js`.**
Каждый метод помечен `TODO(api)` с предполагаемым маршрутом и формой ответа.
При подключении бэкенда меняются только тела этих методов — остальной код
не трогается.

| Метод `api` | Маршрут (предложение) | Что делает |
|---|---|---|
| `loadConfig` | `GET /api/config` | **подключено** — читает settings.yaml и .env |
| `saveConfig` | `PUT /api/config` | **подключено** — пишет изменённые листья |
| `startAgent` / `stopAgent` | `POST /api/agent/start` / `/stop` | **подключено** — запуск `src/main.py`, сигнал `agent.stop` |
| `agentStatus` | `GET /api/agent/status` | **подключено** — работает ли, pid, время работы |
| `tickState` | `GET /api/tick` | **подключено** — фаза такта, шаг ReAct, обратный отсчёт, всплески для пульса |
| `loadLogs` / `subscribeLogs` | `GET /api/logs` + SSE | **подключено** — хвост `logs/main.log` и живая дозапись |
| `downloadLogs` | `GET /api/logs/download` | **подключено** — отдаёт файл целиком |
| `loadChat` | `GET /api/chat` | **подключено** — переписка из history.json и состояние связи |
| `sendMessage` | `POST /api/chat` | **подключено** — в терминальный канал агента |
| `subscribeChat` | SSE `/api/chat/stream` | **подключено** — реплики агента |
| `loadDbStats` | `GET /api/db/stats` | **подключено** — счётчики трёх баз и размеры каталогов |
| `loadDrives` / `saveDrives` | `GET/PUT /api/drives` | **подключено** — мотиваторы из таблицы `drives` |

одним делегированным слушателем — искать по `data-action` в `index.html`.

## Что уже готово к подключению

**Разбор логов.** `parseLog()` понимает формат `main.log` как есть, включая
многострочные записи (`[Thoughts]`, отчёты субагентов, врезки файлов после
`====`). Подать сырой текст — и всё отрисуется. Демо-срез лежит в
`<script type="text/plain" id="logSeed">`; при интеграции блок удаляется.

**Уровни доступа.** Две независимые шкалы разведены и подписаны по
документации: `host.os.access_level` (SANDBOX / OBSERVER / OPERATOR / ROOT) и
`meta.access_level` (SAFE / CONFIGURATOR / ARCHITECT / CREATOR).

**Приоритеты событий.** Подписи в «Ускорении по приоритету» сверены с
`src/utils/event/registry.py` — все 28 событий разложены по своим уровням.

**Секреты.** Статус «задан / пусто» вычисляется из значения поля, а не хранится
в разметке. Значения `.env` сервер отдаёт как есть — иначе не работает кнопка-глаз
и правка ключа. Это ещё одна причина не выпускать консоль наружу без токена.

**Список ключей LLM.** Произвольной длины, со сквозной перенумерацией
`LLM_API_KEY_N` — как их и собирает `src/main.py` перебором окружения.

### Раздел «Интерфейсы»

82 параметра `interfaces.yaml`, 4 списка и 12 секретов `.env`. Тумблер в шапке
карточки привязан к `<интерфейс>.enabled`, поэтому фильтры «Активные /
Выключенные» считают реальное состояние.

Две вещи пришлось изменить по существу:

* **«Синтез речи» разделён на две карточки** — ElevenLabs и Edge. В конфиге это
  независимые подсистемы, у каждой свой `enabled`; один тумблер в шапке не мог
  означать обе. Карточек стало 18.
* **«Свой эндпоинт» из тумблера стал полем.** В `.env` это URL
  (`ELEVENLABS_API_URL`, `CLOUD_WHISPER_API_URL`), а не флаг: пусто —
  официальный API.

Списки: `code_graph.exclude_dirs`, оба `available_voices` и `web.rss.feeds`.
Последний — список словарей `{name, url}`, для него в `config_io` отдельный
писатель `set_object_list`.

### Как устроена привязка

Атрибут `data-cfg="<источник>:<путь>"` на контроле; тот же ключ — в
`src/web/schema.py`. Фронтенд и бэкенд не могут разъехаться: сервер отдаёт
словарь ровно этих ключей, консоль раскладывает его по `[data-cfg]`.

```html
<input data-cfg="settings:llm.temperature">
<span class="sw" role="switch" data-cfg="settings:llm.is_multimodal"></span>
<input type="password" data-cfg="env:LLM_API_URL">
```

Чтобы подключить следующую вкладку, нужно: дописать поля в `schema.py` и
проставить те же `data-cfg` в разметке. Больше ничего.

### Про запись

Полный round-trip через ruamel.yaml сохраняет комментарии, но нормализует то,
чего не касались: отступы списков, хвостовые пробелы, блок `system.subconscious`
с нестандартным отступом — и теряет комментарий, привязанный к последнему
элементу списка. Поэтому читаем через ruamel, а **пишем построчно**: меняется
ровно та строка, которую правил человек. Проверено — в `git diff` попадают
только изменённые строки, CRLF и комментарии целы, `1.0` не превращается в `1`.

`.env` правится точечно: значения заменяются на месте, нумерованные ключи
(`LLM_API_KEY_N`) перенумеровываются сквозняком, закомментированные заготовки
убираются.

## Что делать дальше

### Управление агентом

Кнопки «Запустить» и «Остановить» в шапке работают: поднимают `src/main.py`
отдельным процессом и просят его завершиться файлом-сигналом `agent.stop`.
Состояние опрашивается каждые 4 секунды, поэтому шапка показывает правду, даже
если агента запустили из CLI.

Своя проверка «работает ли» вместо штатной `is_agent_running()`: та при
отрицательном ответе **удаляет** pid- и lock-файлы, а опрос по таймеру снёс бы
их ровно тогда, когда агент их создаёт. Здесь только чтение pid-файла и
проверка процесса через psutil.

Отдельное состояние `starting`: на первом запуске агент несколько минут качает
модель эмбеддингов и всё это время не зарегистрирован. Показывать «остановлен»
в этот момент — врать, поэтому в шапке пишется «Запускается».

### Журнал

Вкладка «Логи» читает настоящий `logs/main.log`: при открытии приходит хвост
(256 КБ), дальше дозапись через Server-Sent Events с опросом раз в секунду.

Тонкости, которые пришлось учесть:

* читаем по смещению в байтах, а не по строкам;
* строку без перевода придерживаем — её дописывают прямо сейчас, и отдать её
  значит показать половину записи;
* если файл стал короче прежнего смещения, значит сработала ротация
  (`system.logging.max_file_size_mb`) — начинаем сначала, иначе поток замолчал
  бы навсегда;
* строка без метки времени — продолжение предыдущей записи, и склейка
  переживает границу между порциями потока: многострочные блоки `[Thoughts]`
  приходят разрезанными.

Токен из адреса страницы подставляется во все запросы: `EventSource` не умеет
задавать заголовки, а без токена сервер ответит 401.

### Мотиваторы

Шкалы читаются из таблицы `drives` базы агента
(`src/utils/local/data/sql/db/agent.db`). Дефицит нигде не хранится — он
вычисляется из `last_satisfied_at`, поэтому шкалы обновляются раз в десять
секунд, пока вкладка видна.

Формула повторяет `_calculate_deficit` из
`src/l1_databases/sql/management/drives/crud.py`, включая нелинейное
накопление при `dynamic_reduction`. Расходиться им нельзя, поэтому есть тест,
сверяющий обе реализации на пятистах случайных наборах.

Два вида мотиваторов ведут себя по-разному, и это видно в интерфейсе:

* **фундаментальные** описаны в `settings.yaml`; при каждом старте фреймворк
  перезаписывает их значения в базе из конфига, а выключенные удаляет. Поля
  привязаны к конфигу. Если база разошлась с конфигом, консоль пишет, что
  настройки применятся при следующем запуске;
* **свои** созданы агентом и живут только в базе — их карточки строятся на
  лету, с пометкой «свой», а правки идут прямо в SQLite. Фундаментальные через
  этот путь не проходят: правка базы выглядела бы применённой, но исчезла бы
  при перезапуске.

База открывается только для чтения — агент работает и держит её открытой.
Для записи короткий таймаут, и при занятой базе консоль честно об этом скажет.

### Шапка: такт, шаг и обратный отсчёт

`src/web/tick.py` + `GET /api/tick`.

Своего состояния агент наружу не отдаёт: `AgentState` и
`Heartbeat._next_tick_time` живут в памяти его процесса, а консоль — процесс
отдельный. Поэтому шапка **восстанавливается по `logs/main.log`**: сервер
разбирает строки фреймворка и повторяет его же расчёт следующего такта.

Опорные строки и что из них берётся:

| Строка журнала | Что даёт |
| --- | --- |
| `[ReAct] Reasoning cycle initialized. Reason: X` | агент проснулся, причина, модель |
| `[ReAct] Step N/M.` | шаг ReAct; строку пишут два логгера, считаем один раз |
| `[ReAct] ... Concluding cycle.` | конец цикла — **отсюда** отсчитывается следующий такт |
| `[Heartbeat] ... Until wakeup: N sec.` | готовый остаток при событии-ускорителе, самый точный якорь |
| `[Heartbeat] Custom sleep mode engaged for HH:MM:SS` | свой сон и его глубина |
| `[Heartbeat] Interrupted current ReAct cycle` | пробуждение немедленное |
| `[Heartbeat] Orchestrator stopped.` | агент вышел из такта |
| `[Agent Action] Class.method(...)`, `[LLM]`, `[Vector-Graph RAG]` | чем занят прямо сейчас |

Две тонкости, повторённые за фреймворком:

* следующий такт назначается от **конца** цикла, а не от начала: пока идёт
  рассуждение, время до пробуждения уже течёт;
* если цикл начался из своего сна, интервал по его завершении **не**
  применяется — следующий такт идёт сразу.

Одно место, где журнал молчит: цикл, упёршийся в лимит шагов, выходит из
`while` без записи. Он признаётся законченным, только когда модель на последнем
шаге уже ответила и после этого журнал молчит 20 секунд, — иначе ожидание
ответа модели принималось бы за конец такта.

Всплески на кардиограмме идут из поля `events` с возрастающим `seq`: клиент
рисует только то, чего ещё не видел. При открытии консоли состояние
восстанавливается по хвосту журнала **без** всплесков — иначе пульс выдал бы
очередь ударов, которых пользователь не застал.

### Вкладка «База данных»

`src/web/database.py` + `GET /api/db/stats`, `POST /api/db/wipe`.

Три хранилища ведут себя по-разному, пока агент работает, и это определило всё
устройство раздела:

| База | Чтение при живом агенте | Как |
| --- | --- | --- |
| Реляционная (SQLite) | да | обычное подключение `mode=ro` |
| Векторная (Qdrant, локальный режим) | да | клиент недоступен — каталог под `.lock`, но точки лежат в `collection/<имя>/storage.sqlite`, читаем его напрямую |
| Граф (Kuzu) | **нет** | исключительная блокировка файла: второй процесс не может ни открыть его, ни скопировать |

Про граф интерфейс так и пишет — «агент держит базу». Ноль здесь означал бы
«пусто», а спутать это с «не смогли прочитать» перед кнопкой «Очистить» дорого.
CLI фреймворка в этом месте показывает нули: `_get_vector_stats` и
`_get_graph_stats` глушат исключение через `except Exception: pass`.

**Очистка возможна только на остановленном агенте.** Это правило самого
фреймворка (`database_manager_screen` отказывается работать при живом агенте
«to avoid SQLite Locks»), а для векторной и графовой баз ещё и физика. Сервер
отвечает `409` с `needsStop`, кнопки в интерфейсе заперты, пока агент жив.

Области очистки (`data-scope`) — устойчивые ключи, а не подписи: `sql.tasks`,
`sql.all`, `vector.knowledge`, `graph.concepts`, `interfaces.all` и так далее.
Русские имена живут на сервере, в `SCOPE_LABELS`; тест сверяет, что каждая
кнопка в разметке известна серверу и наоборот.

**Скачанные модели эмбеддингов** — отдельный случай. Веса лежат в
`vector/embeddings` и весят сотни мегабайт; после смены модели в «Память →
Векторная база» прежние остаются на диске навсегда, сами они не удаляются.
Карточка векторной базы показывает список с размерами и помечает используемую.

Имя каталога и имя модели не совпадают: fastembed качает свою ONNX-сборку, и
`sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2` лежит как
`models--qdrant--paraphrase-multilingual-MiniLM-L12-v2-onnx-Q`. Соответствие
спрашиваем у самого fastembed (`TextEmbedding.list_supported_models()`), чтобы
не держать копию списка, которая устареет.

Области здесь динамические — `embeddings.<каталог>`, — поэтому в `SCOPE_LABELS`
их нет и проверяются они иначе: каталог должен реально лежать в кэше и не
выводить за его пределы. Отдельный набор тестов бьёт по этому месту `..`,
разделителями пути и служебными каталогами.

Два места, где мы расходимся с CLI осознанно:

* коллекция Qdrant **очищается**, а не пересоздаётся. CLI подставляет
  `vector_size` из settings.yaml — а это поле редактируется на вкладке
  «Память», и пересозданная коллекция может получить размерность,
  несовместимую с накопленными эмбеддингами;
* `_clear_sandbox` продублирован, а не импортирован: модуль CLI тянет за собой
  questionary и весь интерфейс командной строки. Тест сверяет состав служебных
  каталогов песочницы с оригиналом.

Кстати: в локальном Qdrant payload-индексы не работают вовсе («Payload indexes
have no effect in the local Qdrant»), так что вызов `create_payload_index` в
`l1_databases/vector/db.py` — пустая операция до перехода на серверный Qdrant.

### Вкладка «Чат»

`src/web/chat.py` + `GET/POST /api/chat`, SSE `/api/chat/stream`.

Своего канала консоль не изобретает: у фреймворка уже есть канал оператора —
`HostTerminalClient` (`src/l2_interfaces/host/terminal/client.py`). Это
TCP-сервер на случайном порту, который агент записывает в `terminal.port`; к
нему подключается CLI-чат. Консоль становится вторым таким клиентом:

1. читает порт из файла;
2. подключается и посылает строку `JAWL_HANDSHAKE` — без неё агент молча рвёт
   соединение, так он отшивает сканеры портов;
3. шлёт `{"text": "..."}` построчно;
4. читает ответы `{"text": ..., "time": ...}` тем же построчным JSON.

Переписка лежит в `history.json` и пишется самим агентом, поэтому видна и при
остановленном агенте.

**Подключение не бесплатно.** Первый клиент поднимает `HOST_TERMINAL_OPENED`,
последний — `HOST_TERMINAL_CLOSED`, а каждое сообщение публикует
`HOST_TERMINAL_MESSAGE` уровня CRITICAL, то есть будит агента немедленно. Из
этого следуют два решения:

* соединение держится, только пока **выбран раздел «Чат»**, а не всё время
  работы консоли — иначе агенту сообщалось бы, что оператор смотрит в терминал,
  когда никто не смотрит;
* на `visibilityState` при этом не смотрим. Свёрнутое окно браузера — не
  «оператор ушёл»: чат по-прежнему открыт, как остаётся открытым окно CLI. Иначе
  каждый переход на соседнюю вкладку слал бы пару «закрыт»/«открыт», а открытие
  ещё и ускоряет агенту пробуждение.

Разрыв на перезагрузку страницы гасится задержкой в пять секунд перед закрытием
соединения — иначе обновление вкладки выглядело бы для агента как уход и
возвращение оператора.

**Чат целиком зависит от `host.terminal.enabled`.** Выключен — агент не
поднимает TCP-сервер, и разговаривать не через что. Это настройка, а не сбой,
поэтому состояние `disabled` отделено от `offline`: поле ввода блокируется,
причина названа, и кнопка «Открыть настройку» ведёт прямо к нужному
выключателю в разделе «Интерфейсы».

Три причины молчания различаются, потому что действия у них разные:

| Что видно | Что произошло | Что делать |
| --- | --- | --- |
| «Интерфейс «Терминал» выключен» | `host.terminal.enabled: false` | включить и перезапустить агента |
| «агент запущен без терминала — перезапустите его» | настройку включили после старта | перезапустить агента |
| «агент не запущен» | файла порта нет, агента нет | запустить агента |
| «агент не отвечает на порту N» | файл порта остался от прошлого запуска | запустить агента |

Кода ошибки сокета в интерфейс не попадает: `[WinError 1225] Удалённый
компьютер отклонил это сетевое подключение` не говорит пользователю ничего о
том, что нужно сделать.

Две тонкости протокола:

* он построчный, поэтому переводы строк внутри сообщения схлопываются в пробелы:
  иначе агент получил бы только первую строку;
* история из файла и буфер потока перекрываются — агент пишет в файл те же
  реплики, что рассылает подписчикам. Клиент при загрузке догоняет счётчик
  сервера, иначе каждая реплика показывалась бы дважды.

### 1. Живые данные

Из макета остались только счётчики «Навыков в реестре» на карточках
интерфейсов — они помечены `data-demo`, их видно поиском.

### 2. Параметры без полей в интерфейсе

Эти ключи существуют в `settings.yaml`, но контролов для них нет — их не
показать и не изменить:

- `system.logging.max_file_size_mb`, `system.logging.backup_count`
- `system.swarm.context_depth.*` — привязаны 2 из 7
- `context_depth.tick_action_short_max_chars`, `tick_result_short_max_chars`
- `system.subconscious.patterns.*.activation_limit_ticks` — есть только тумблеры
- выключатели модулей `db.sql.{tasks,notes,personality_traits,mental_states}.enabled`
  — в карточке «Реляционная база» только лимиты
- `SUB_LLM_API_KEY_N` — привязан только первый ключ, редактора списка нет

Всё перечисленное — параметры без контролов в интерфейсе. Пути в `schema.py`
и поля в разметке сходятся один в один, это проверяется тестами.

### 3. Проверить, что перечитывается на ходу

В шапке вкладки «Параметры» стоит утверждение «изменения применяются на
следующем такте — перезапуск не нужен». Оно **не проверено**. Нужно пройти по
параметрам и честно пометить те, что требуют рестарта; `saveConfig` для этого
и возвращает `restartRequired`.

### 4. Конфликт с Gatekeeper

В карточке «Хост · ОС» есть запрет `env_access` — он про **агента**. Консоль
пишет `.env` от лица человека, это другой субъект. Развести явно в коде и в
интерфейсе, чтобы не выглядело дырой в модели доступа.

### 5. Кнопка «Открыть папку» на удалённой машине

`openDir` запускает файловый менеджер локально. Если консоль открыта не на той
машине, где крутится агент, кнопку надо прятать.

## Что в прототипе выдумано

В разделе «Параметры» выдуманных значений не осталось — поля наполняются из
файлов. Заодно удалено то, чему в конфиге вообще нет соответствия:

- «Последняя симуляция» — нарисованное дерево вариантов;
- «Роли» в карточке роя — права навыков задаются декораторами
  `@skill(swarm=[...])` в коде, настройкой они не являются;
- «Заполнение · 26%» у графа знаний — это состояние базы, а не настройка
  (полоски дефицита у мотиваторов с тех пор подключены к таблице `drives`);
- выпадающий список моделей эмбеддингов заменён текстовым полем: имя модели —
  свободная строка (`sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`),
  в фиксированный список она не помещалась.

Демо-данных больше не осталось нигде, кроме счётчиков навыков.

Счётчики «Навыков в реестре» на карточках интерфейсов — числа демонстрационные,
но сама величина отслеживаема: `_REGISTRY` в `src/l3_agent/skills/registry.py`.

Пульс и таймер такта больше не выдуманы: форма кардиограммы рисуется локально,
но каждый всплеск и обратный отсчёт приходят из `GET /api/tick` — см. «Шапка:
такт, шаг и обратный отсчёт».
